# /build — 执行当前任务

## 触发时机

日常开发，高频使用。执行 /plan 拆出的任务。

## 执行步骤

1. 读取 `docs/state.md`（找到当前 pending 或 in_progress 的任务）
2. 如果没有待执行的任务，提示用户先 /plan
3. 读取 `docs/conventions.md`（编码规范）
4. 涉及关键技术时读取 `docs/tech-patterns.md`（踩坑点）
5. **任务层拷打**（见下方）
6. **提方案**：说明要做什么、涉及哪些文件、怎么做
7. **等用户确认**后写代码
8. **轻量自检**：
   - 编译/构建能否通过
   - 功能能否基本运行
   - 有没有违反 conventions 和 CLAUDE.md 红线
9. 更新 `docs/state.md`（标记 ✅ completed）
10. 追加 `docs/dev-log.md`（记录做了什么，没有涉及的分类不写）
11. 问用户：继续下一个任务？（提示可以 /plan 拆下一个）

## 任务层拷打规则

在提方案之前，从四个维度拷打用户，确认设计方案再动手。

### 核心原则：逐一讨论，不一股脑列出

**禁止**把所有决策一次性列出让用户选。决策之间有依赖关系，前面的选择会影响后面的问题。

正确节奏：
1. 问**第一个**决策（给选项 + 理由 + 建议）
2. 等用户回答
3. 根据回答，引出**下一个**相关决策
4. 重复，直到所有关键决策确认
5. 汇总确认 → 写代码

每个问题必须同时给出 **选项 + 建议**，不能只问不给方向：

```
这个问题有两种做法：

  A. 方案一 — 描述 + 优劣
  B. 方案二 — 描述 + 优劣

  我建议 X，因为... 你怎么看？
```

### 四个拷打维度（内部思考框架，不一次性呈现给用户）

用这四个维度组织思考，但**每次只问一个问题**，按依赖顺序推进：

#### 1. 架构决策

这个任务有几种实现方案？每种的优劣是什么？

- 给出 2-3 个方案选项（A/B/C）
- 说明每个方案的优劣
- 给出推荐方案和理由
- 关注点：代码放在哪一层、用什么设计模式、是否需要新类/新接口

#### 2. 技术细节

这个任务涉及哪些技术点？有哪些坑要提前避开？

- 引用 `docs/tech-patterns.md` 中相关的踩坑点
- 如果有 API 选型、库版本、配置项等需要确认的技术细节，在这里问
- 关注点：依赖版本、配置项、API 用法、兼容性

#### 3. 边界情况

这个任务可能遇到什么异常或边界情况？怎么处理？

- 列举 2-3 个边界情况
- 每个给出处理建议
- 关注点：空值、并发、超时、用户误操作、数据不一致

#### 4. 代码接点

这个任务和已有代码有哪些交互点？会影响什么？

- 列出涉及的已有文件和模块
- 说明是新增、修改还是复用
- 说明对现有功能的影响（无影响 / 需要适配 / 可能破坏）
- 关注点：现有接口是否够用、配置是否需要修改、是否需要新依赖

### 拷打的深度

根据任务复杂度调整，但始终遵循"逐一讨论"原则：

- **简单任务**（如新增一个接口字段）：1-2 个决策，几轮对话搞定
- **中等任务**（如新增一个 CRUD 模块）：3-5 个决策，逐个讨论
- **复杂任务**（如 SSE 流式对话）：5-7 个决策，可能需要 10+ 轮对话

## 变更处理

用户对已完成任务提出修改时：
1. 确认修改意图
2. 列出受影响的后续任务
3. 更新 plan.md 和 state.md
4. 重新实现

## 错误处理

- 自检不通过：任务保持 in_progress，分析失败原因，修复后重新自检
- 用户对方案不满意：重新提方案，不强行推进
- 编译/构建失败：先修到能编译，再继续其他工作

## 输出

用户看到：拷打问题 → 方案 → 代码 → 自检结果
文件更新：state.md + dev-log.md + 代码文件
