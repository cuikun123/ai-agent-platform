# /plan — 拆解下一个任务

## 触发时机

- 迭代开始时，拆第一个任务
- /build 完成一个任务后，拆下一个
- 需要调整计划时

## 执行步骤

1. 读取 `docs/plan.md`（看当前迭代的大方向、验收标准和已完成任务）
2. 读取 `docs/state.md`（看进行中的任务）
3. **拷打阶段**（根据场景选择类型，见下方）
4. 拆解任务，向用户提建议：
   - 基于大方向判断优先级
   - 说明为什么这个任务应该下一个做
   - 给出任务描述（一句话，可验证的小功能点）
5. 用户确认后，写入：
   - `docs/plan.md` — 追加新任务行（状态 ⬜）
   - `docs/state.md` — 同步更新

## 拷打规则

### 什么时候拷打

- 当前迭代无 pending 任务 → **方向性拷打**（迭代启动）
- 当前迭代有已完成任务 → **承接性拷打**（迭代进行中）
- 用户主动调整计划 → **承接性拷打**

### 拷打格式

每个问题必须同时给出 **选项 + 建议**，不能只问不给方向：

```
你想要的是什么？

  A. 选项一 — 描述
  B. 选项二 — 描述
  C. 选项三 — 描述

  我建议 X，因为... 你怎么看？
```

用户可以选 A/B/C，也可以在此基础上补充或修改。

### 方向性拷打（迭代启动时）

问 3-5 个问题，理清整个迭代的方向：

1. **最小可用版本** — 这个迭代最核心的是什么？什么可以后做？
   - 给出"只做核心" / "核心 + 次要" / "全做"的选项
2. **优先级排序** — 列出迭代里的主要模块，问哪个最重要
3. **参考产品** — 有没有参考的竞品或体验？
4. **风险预判** — 哪个环节你最不确定？最担心什么？
5. **约束条件** — 有没有时间、资源、技术上的限制？

### 承接性拷打（迭代进行中）

问 1-2 个问题，理清下一个任务的方向：

1. **上一个任务的延伸** — 上一个做完了，接下来有两个方向 A 和 B
   - 说明每个方向的优劣
   - 给出建议
2. **依赖关系** — 这个任务需要等别的任务先完成吗？

## 任务颗粒度

- ✅ 刚好：一个可验证的小功能点，做完就能测
- ❌ 太粗：一个完整模块（如"用户认证"）
- ❌ 太细：单个文件（如"创建 RegisterRequest.java"）
- 示例：✅ "注册接口 — Controller + 参数校验"

## 输出

用户看到：拷打问题 → 任务建议 + 理由
文件更新：plan.md + state.md
